Chuleta rápida para entrevista: RentingPrototype
===============================================

1. Qué es el proyecto
---------------------

API REST en .NET 9 con Minimal API para gestionar un prototipo de renting:
- alta de vehículos,
- consulta de vehículos,
- alquiler,
- devolución,
- historial.

Objetivo técnico:
- demostrar diseño limpio,
- separación de capas,
- DDD ligero,
- puertos y adaptadores,
- manejo de errores,
- testing y Docker.


2. Cómo está separada la solución
---------------------------------

`RentingPrototype.Domain`
- Núcleo de negocio.
- Entidades: `Vehicle`, `Rental`.
- Value Objects: `VehicleId`, `LicensePlate`, `ManufactureDateOnly`.
- Domain Events.
- Excepciones de dominio.

`RentingPrototype.Application`
- Casos de uso.
- Handlers de comandos y queries.
- Puertos: repositorios, unit of work, dispatcher de eventos, log sink.
- Orquesta dominio e infraestructura sin conocer implementaciones concretas.

`RentingPrototype.Api`
- Adaptador de entrada HTTP.
- Endpoints Minimal API.
- Contratos HTTP.
- Validación superficial de request.

`RentingPrototype.Infrastructure`
- Adaptadores de salida.
- Sqlite + Dapper.
- Repositorios concretos.
- `SqliteUnitOfWork`.
- inicialización de base de datos.
- logging estructurado a fichero.

`RentingPrototype.Host`
- Ejecutable real.
- Composition root.
- Configura DI, manejo global de excepciones, OpenAPI y Scalar.


3. Cómo defender la arquitectura
--------------------------------

Mensaje corto:

"He organizado la solución en dominio, aplicación, adaptadores HTTP, infraestructura y host. El dominio contiene las reglas puras. La aplicación define los casos de uso y los puertos. La infraestructura implementa esos puertos. La API solo adapta HTTP a aplicación. El host compone todo."

Si te dicen "¿es hexagonal de verdad?":
- Sí en el sentido práctico:
  - aplicación define puertos,
  - infraestructura implementa adaptadores,
  - API es adaptador de entrada,
  - dominio queda aislado.
- No he buscado pureza académica extrema, sino una estructura defendible para una prueba técnica.


4. Flujo de una petición correcta
---------------------------------

Ejemplo: `POST /vehicles`

1. Llega HTTP.
2. Minimal API hace model binding a `CreateVehicleRequest`.
3. El endpoint valida DataAnnotations.
4. El endpoint construye `CreateVehicleCommandDto`.
5. El handler llama al dominio: `Vehicle.Create(...)`.
6. El dominio valida reglas y genera `VehicleCreatedDomainEvent`.
7. El handler abre transacción con `IUnitOfWork`.
8. El repositorio guarda en Sqlite con Dapper.
9. Se hace commit.
10. Se despachan domain events.
11. Se devuelve `201 Created`.


5. Flujo de error por validación
--------------------------------

Ejemplo: request HTTP inválida.

1. Llega el JSON.
2. El endpoint valida el request.
3. Si falla, devuelve `ValidationProblem`.
4. Normalmente responde `400 Bad Request`.

Idea clave:
- esto corta el flujo antes de tocar aplicación, dominio o base de datos.


6. Flujo de error por excepción
-------------------------------

Ejemplo: cliente intenta alquilar un segundo vehículo sin devolver el primero.

1. El endpoint recibe request válida.
2. El handler consulta repositorios.
3. Detecta incumplimiento de regla.
4. Lanza `BusinessRuleViolationException`.
5. La excepción sube al `GlobalExceptionHandler`.
6. El handler global la transforma en `409 Conflict`.
7. Se devuelve `ProblemDetails`.
8. Además se registra log estructurado con `traceId`.

Idea clave:
- los endpoints no repiten `try/catch`,
- el error queda centralizado y consistente.


7. Qué aporta DDD aquí
----------------------

- Entidades con reglas de negocio dentro.
- Value Objects para evitar primitivas débiles.
- Domain Events para reflejar hechos relevantes del negocio.
- Excepciones tipadas para reglas e invariantes.

Mensaje defendible:

"No he montado un DDD gigantesco, pero sí un DDD ligero y útil: el negocio vive en dominio y no en los endpoints."


8. Qué aporta CQRS aquí
-----------------------

- Separación simple entre escritura y lectura.
- Handlers de comando para cambios.
- Handlers/query repos para consultas.
- No hay una infraestructura compleja de mensajería, porque no hacía falta para esta prueba.


9. Testing: cómo explicarlo en 30 segundos
------------------------------------------

Hay tres niveles:

`Unit tests`
- prueban lógica aislada con fakes.
- ejemplo: `CreateVehicleHandlerTests`.

`Integration tests`
- prueban extremo a extremo dentro del proceso.
- ejemplo: `POST /vehicles` y comprobar que se escribe el domain event en logs.

`Host tests`
- prueban composición y arranque.
- ejemplo: comprobar que DI registra `IUnitOfWork`, repositorios, OpenAPI y endpoints.

Mensaje defendible:

"No me limité a probar clases sueltas; también probé que la aplicación ensamblada funciona."


10. Persistencia e infraestructura
----------------------------------

Base de datos:
- Sqlite.

Acceso a datos:
- Dapper.

Motivo:
- menos complejidad,
- SQL explícito,
- muy defendible para una prueba técnica.

Transacciones:
- `SqliteUnitOfWork`.

Inicialización:
- al arrancar, si la base no existe, se crea y se aplica el schema.


11. Logging y errores
---------------------

- Logging estructurado en JSON.
- Se registran excepciones y domain events.
- Las excepciones se transforman en respuestas HTTP coherentes.
- Los errores no controlados devuelven `500` sin filtrar detalles internos al cliente.


12. Docker
----------

Qué hace:
- el `Dockerfile` publica `RentingPrototype.Host`,
- el contenedor arranca `RentingPrototype.Host.dll`,
- `docker compose` monta datos, schema y logs.

Comandos clave:

`docker build -t rentingprototype:local .`

`docker run --rm -p 8080:8080 rentingprototype:local`

`docker compose up --build`


13. Fortalezas que puedes vender
--------------------------------

- Separación clara de responsabilidades.
- Dominio razonablemente bien encapsulado.
- Puertos y adaptadores bien visibles.
- Manejo global de excepciones.
- Logging estructurado.
- Tests en varios niveles.
- Proyecto ejecutable localmente y en Docker.


14. Limitaciones que puedes reconocer sin problema
--------------------------------------------------

- No busca ser un producto enterprise completo.
- La observabilidad está en un nivel razonable para prueba técnica, no con dashboarding ni telemetry avanzada.
- CQRS y DDD están aplicados de forma ligera, no maximalista.
- Sqlite es una elección pragmática para prototipo.

Mensaje defendible:

"He priorizado decisiones proporcionales al alcance de una prueba técnica: suficiente calidad arquitectónica sin sobrediseñar."


15. Frase final para cerrar bien
--------------------------------

"Mi intención con esta prueba no fue solo hacer que funcionase, sino que fuese fácil de explicar, fácil de evolucionar y técnicamente defendible."
