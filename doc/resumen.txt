============================================================
1) VISTA GENERAL DEL SISTEMA
============================================================

RentingPrototype es una API REST en .NET 9 (Minimal API) para gestionar:
- Alta de vehiculos.
- Consulta de vehiculos (todos, por id, disponibles).
- Inicio de alquiler (rent).
- Cierre de alquiler (return).
- Consulta de historico de alquileres por vehiculo y por cliente.

La persistencia usa SQLite + Dapper, con esquema SQL y seed inicial.

Arquitectura principal:
- Arquitectura por capas (Api / Application / Domain / Infrastructure).
- CQRS ligero (lecturas y escrituras separadas por handlers y repositorios).
- Repository pattern (abstraccion de acceso a datos).
- Unit of Work (frontera transaccional en comandos).

3) FLUJO DE UNA PETICION (EJEMPLO REAL)
============================================================

Ejemplo: POST /rentals/rent-vehicle

1. Endpoint Minimal API (RentalEndpoints) recibe DTO.
2. Inyecta CreateRentalHandler desde DI.
3. Handler valida precondiciones consultando IRentalQueryRepository:
   - Cliente con alquiler abierto.
   - Vehiculo con alquiler abierto.
4. Si pasa validacion, crea entidad Rental del dominio.
5. Inicia transaccion con IUnitOfWork (BeginAsync).
6. Persiste via IRentalCommandRepository.CreateAsync.
7. Commit transaccional.
8. Devuelve 201 Created con id.
9. Si algo falla, rollback y excepcion traducida a HTTP (400/500 en endpoint).

Observacion importante para entrevista:
- Hay doble proteccion de consistencia:
  - Validacion en aplicacion (rapida y explicita).
  - Constraint unico parcial en DB (ultima barrera ante concurrencia).

4) CAPA DOMAIN (REGLAS DE NEGOCIO)
============================================================

Entidad Vehicle:
- Invariantes:
  - id no vacio.
  - matricula requerida y max 20.
  - marca requerida y max 100.
  - modelo requerido y max 100.
  - fecha de fabricacion no mas antigua de 5 anios.
- Normaliza strings con Trim().
- Fuerza DateTimeKind.Utc en manufactureDateUtc.

Entidad Rental:
- Invariantes:
  - customerId no vacio.
  - vehicleId no vacio.
  - startDate no puede estar en futuro.
  - endDate (si existe) no puede ser anterior a startDate.

Decision clave:
- El dominio concentra reglas de negocio, no SQL ni HTTP.
- Esto facilita test unitarios directos y evita logica de negocio en controladores.

Trade-off:
- Rental.Create usa DateTime.UtcNow internamente para comparar fechas futuras. Esto es simple, pero menos controlable en tests que inyectar un reloj (IClock).

5) CAPA APPLICATION (CASOS DE USO)
============================================================

Patron aplicado:
- Handlers por caso de uso, separados en comandos (write) y queries (read).

Comandos:
- CreateVehicleHandler
- CreateRentalHandler
- UpdateRentalHandler

Queries:
- GetVehicleByIdQueryHandler
- GetAllVehiclesQueryHandler
- GetAvailableVehiclesQueryHandler
- GetRentalByIdQueryHandler
- VehicleRentalHistoryQueryHandler
- CustomerRentalHistoryQueryHandler

Abstracciones:
- IUnitOfWork: Begin/Commit/Rollback
- Interfaces de repositorio por agregado y por tipo de operacion.
- IQueryHandler<TQuery, TResult> para homogeneizar consultas.

Decision de diseno:
- CQRS ligero: separa responsabilidades sin introducir bus de comandos/eventos.
- Bueno para prototipo: bajo coste cognitivo, estructura clara, crecimiento gradual.

Trade-off:
- Aun no hay pipeline cross-cutting (validacion centralizada, logging, metrics, retries).
- El manejo de errores esta repetido en endpoints (try/catch por metodo).

============================================================
6) CAPA INFRASTRUCTURE (PERSISTENCIA)
============================================================

Tecnologias:
- SQLite (archivo local o in-memory en tests).
- Dapper para mapeo ligero SQL -> DTO/entidades.

Implementaciones clave:
- SqliteConnectionFactory: crea conexiones a partir de connection string.
- SqliteUnitOfWork: abre conexion, inicia transaccion y gestiona ciclo de vida.
- Repositorios de comando usan SqliteUnitOfWork (misma transaccion).
- Repositorios de query abren conexion por operacion (sin transaccion).

Decision de diseno:
- SQL explicito en repositorios (sin ORM pesado) para control fino.
- Transacciones solo en escrituras.

Trade-off:
- Mas control y rendimiento predecible, pero mas codigo SQL manual.
- Riesgo de drift entre dominio y SQL si no se testea.

Detalle relevante para entrevista:
- DTOs de lectura tienen constructores que parsean strings (GUID/Date) porque SQLite devuelve texto y Dapper materializa por nombre.

7) BASE DE DATOS: SCHEMA, CONSTRAINTS Y SEED
============================================================

Archivo: src/RentingPrototype.Infrastructure/Persistence/Schema/rentingprototype-schema.sql

Tablas:
- vehicles
- customers
- rental_history

Constraints relevantes:
- PK en las tres tablas.
- FK en rental_history hacia vehicles y customers.
- CHECK de longitudes (matricula, marca, etc).
- CHECK: end_date >= start_date.
- UNIQUE en document_id de customer.
- UNIQUE en license_plate de vehicle.
- UNIQUE parcial para alquiler abierto:
  - un solo alquiler abierto por cliente (end_date IS NULL)
  - un solo alquiler abierto por vehiculo (end_date IS NULL)

Semilla de datos:
- 10 clientes.
- 20 vehiculos.
- 40 alquileres historicos.

Decision de diseno:
- Seed de negocio suficiente para probar queries de historico y disponibilidad sin dependencias externas.

11) DECISIONES DE DISENO IMPORTANTES Y JUSTIFICACION
============================================================

1. Minimal API en lugar de Controllers
- Ventaja: menos friccion, ideal para prototipo, lectura rapida.
- Coste: menos estructura out-of-the-box para filtros/pipelines complejos.

2. Dapper + SQL explicito en lugar de EF Core
- Ventaja: control exacto de queries y schema, simple para SQLite.
- Coste: mapping manual y mantenimiento SQL.

3. CQRS ligero
- Ventaja: separar lectura/escritura mejora claridad y evolucion.
- Coste: mas clases/DTOs que enfoque CRUD puro.

4. UoW transaccional en comandos
- Ventaja: atomicidad y rollback claro.
- Coste: requiere disciplina en repositorios para respetar transaccion activa.

5. Validacion duplicada (dominio + DB)
- Ventaja: defensa en profundidad.
- Coste: mantener consistencia entre capas.

6. SQLite como almacenamiento principal
- Ventaja: cero infraestructura externa, perfecto para demo/POC.
- Coste: limitaciones de concurrencia y escalado frente a PostgreSQL/SQL Server.

12) RIESGOS / LIMITACIONES ACTUALES (PARA DISCUTIR EN ENTREVISTA)
============================================================

1. Concurrencia entre chequeo y escritura
- En CreateRentalHandler se chequea "open rental" antes de insertar.
- Puede haber carrera; mitigado por unique indexes parciales en DB.
- Recomendacion: capturar violacion de constraint y traducir a error de dominio mas explicito.

2. Manejo de errores repetido en endpoints
- Mucho try/catch duplicado.
- Recomendacion: middleware de excepciones global + problem details.

3. Contrato 404 vs lista vacia en historico
- Endpoints tienen logica de 404 por null, pero repos devuelven listas.
- Recomendacion: fijar contrato explicito y simplificar endpoint.

4. Falta de autenticacion/autorizacion
- Correcto para prototipo, pero no productivo.

5. Sin observabilidad avanzada
- Faltan tracing/metrics estructuradas.

6. SQLite en contenedor sin volumen
- Riesgo de perdida de estado al recrear contenedor.

7. Dos soluciones en repo
- RentingPrototype.sln (completa) y src/src.sln (parcial, no tracked actualmente).
- Conviene definir una unica entrada para reducir confusion.

14) PREGUNTAS PROBABLES EN ENTREVISTA Y RESPUESTA CORTA
============================================================

P: Por que CQRS y no CRUD simple?
R: Para separar claramente lectura y escritura desde el inicio, manteniendo complejidad baja. Facilita evolucion hacia validaciones y optimizaciones especificas por flujo.

P: Como garantizas que no haya dos alquileres abiertos del mismo vehiculo?
R: En aplicacion verifico precondiciones y en DB lo refuerzo con indice unico parcial sobre vehicle_id donde end_date es null.

P: Por que Dapper?
R: Queria SQL explicito y ligero para una POC con SQLite. Menos abstraccion, control directo de queries y curva rapida.

P: Donde pondrias mejoras para produccion?
R: Middleware global de errores, auth, observabilidad, volumen de datos en Docker, migraciones versionadas y posible paso a Postgres.

P: Como se aislan los tests de integracion?
R: El entorno Testing crea SQLite in-memory con keep-alive por WebApplicationFactory; cada factory usa DB independiente.
